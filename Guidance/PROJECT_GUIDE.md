# 프로젝트 지침 — 노코드 자동화 기초: 워크플로우 설계 (B1-3)

> 이 문서는 미션 수행 전 과정의 기준 문서다. 주제 선정, 도구 선정, 구현, 문서화, 제출까지 이 지침을 따른다.

---

## 0. 핵심 원칙

1. **README가 채점 대상이다.** 평가 도구는 README.md만 읽는다. 보고서·설계문서·캡처 설명이 전부 README 본문에 들어가야 하며, 외부 파일로 분리된 내용은 채점되지 않는다고 간주한다.
2. **동작이 증거다.** 설계 문서만으로는 불합격이다. 모든 주장에는 실행 화면 캡처가 붙어야 한다.
3. **캡처에는 반드시 텍스트 설명을 붙인다.** 이미지가 해석되지 않을 가능성을 전제로, 그 캡처가 무엇을 증명하는지 문장으로 남긴다.
4. **분기는 양쪽 다 태운다.** Filter/Router를 만들었다면 True 경로와 False(또는 Route B) 경로가 각각 최소 1회 실행된 로그가 있어야 한다. 이걸 놓치면 요구사항 미충족이다.
5. **동일 워크플로우로 비교한다.** 프로젝트 1은 "같은 구조"를 서로 다른 도구로 구현해야 비교가 성립한다. 도구별로 시나리오를 바꾸면 안 된다.
6. **무료 플랜 안에서 끝낸다.** 유료 기능을 썼다면 왜 불가피했는지 + 무료 대안을 반드시 보고서에 적는다.
7. **비밀정보는 캡처 전에 가린다.** 사후 수정이 아니라 캡처 직전에 화면을 정리하는 습관을 들인다.


## 2. 워크플로우 주제 선정 기준

주제는 아래 3가지를 동시에 만족해야 한다.

- **분기가 자연스러운가?** 억지로 IF를 끼워 넣은 게 아니라, 업무 자체에 "이러면 A, 저러면 B"가 존재해야 한다.
- **트리거를 내가 마음대로 발생시킬 수 있는가?** 테스트를 10번 이상 돌려야 한다. 한 달에 한 번 발생하는 이벤트는 부적합.
- **무료 커넥터만으로 되는가?** Google Sheets / Gmail / Webhook / Discord / Slack 범위 안에서 설계한다.

### 권장 주제 후보 (프로젝트 1용)
| 후보 | Trigger | 분기 기준 | Action |
|---|---|---|---|
| 문의 접수 분류 | Google Form 제출 (Sheets 신규 행) | 문의 유형 or 긴급도 | Sheets 기록 + 알림 발송 |
| 지출 기록 처리 | Sheets 신규 행 | 금액 임계값 (예: 10만원) | 승인 시트 기록 + 승인 요청 알림 |
| 콘텐츠 검수 | Webhook 수신 | 텍스트 길이/키워드 포함 | 승인 시트 / 보류 시트 분리 + 알림 |

> 프로젝트 1은 **가장 단순한 구조**로 잡는다. 비교가 목적이지 복잡도 과시가 목적이 아니다. 복잡한 건 프로젝트 2에서 한다.

## 3. 도구 선정 지침

### 후보군
- **Make** — 시각적 노드 기반. 무료 Ops 제공. Router/Filter가 무료 범위에서 사용 가능. **1순위 권장**
- **n8n (self-host)** — 셀프호스팅 시 기능 제한 없음. Docker 한 줄로 실행 가능. 과금 리스크 0
- **Zapier** — UI 직관적이나 무료 플랜에서 **Filter/Paths 및 다단계 Zap이 제한**될 수 있음
- **Pipedream / Activepieces** — 대안. 무료 범위 넓은 편

### 선정 시 반드시 착수 전 확인할 것
> 무료 플랜 정책은 자주 바뀐다. 구현 시작 전 각 도구 공식 요금제 페이지에서 아래 3가지를 직접 확인하고 스크린샷을 남긴다.
> 1. 월 무료 실행량(Ops/Tasks)
> 2. **조건 분기(Filter/Router/Paths)가 무료 플랜에 포함되는가**
> 3. 한 시나리오에 몇 개의 스텝까지 허용되는가

이 확인 결과 자체가 비교 보고서의 "무료 플랜 범위" 항목 근거가 된다.

### 권장 조합
**Make + n8n(셀프호스팅)** — 둘 다 조건 분기를 무료로 쓸 수 있고, 노드 기반 vs 노드 기반이라 구조 이식이 쉬우면서도 UX 철학 차이가 뚜렷해 비교 서술이 풍부해진다.

## 4. 비교 항목 (최소 5개, 아래에서 선택 또는 확장)

1. UI/UX — 캔버스 방식 / 리스트 방식, 노드 배치 자유도
2. 설정 난이도 — 첫 시나리오 완성까지 걸린 시간, 막힌 지점
3. 연동 서비스 범위 — 필요한 커넥터 존재 여부, 인증 방식(OAuth/API Key)
4. 무료 플랜 범위 — 실행량, 기능 제한, 실행 주기(폴링 간격)
5. 실행 로그 확인 방식 — 단계별 입출력 데이터 조회 가능 여부, 로그 보관 기간
6. 조건 분기 구현 방식 — Filter vs Router vs Paths의 표현력 차이
7. 에러 핸들링 — 실패 시 재시도, 에러 핸들러 지정 가능 여부
8. 데이터 매핑 — 변수 참조 방식, 배열/JSON 처리 편의성

> **작성 규칙:** "Make가 더 좋다" 같은 인상 비평 금지. "같은 워크플로우 구축에 Make 42분 / n8n 65분 소요, 차이는 인증 설정 단계에서 발생" 식으로 **직접 측정한 근거**를 쓴다.

### 시간 측정 규칙 (설정 난이도 항목의 근거)

시간을 한 덩어리로 재면 비교가 무의미해진다. **두 도구에서 공통으로 반복되는 구간만** 재야 차이를 도구 탓으로 돌릴 수 있다. 아래 3구간으로 나눠 기록한다.

| 구간 | 측정 | 범위 | 성격 |
|---|---|---|---|
| 초기 진입 | ○ (별도 항목) | 도구를 쓸 수 있는 상태로 만들기까지 | 도구별로 내용이 달라 직접 비교 불가, 맥락 정보 |
| **워크플로우 구축** | **○ (핵심 지표)** | 시나리오/워크플로우 생성 → 첫 성공 실행 | 유일하게 동일 조건 비교가 성립하는 구간 |
| 분기 테스트 | ○ | 테스트 데이터 6건 전량 실행 완료까지 | 분기 구현 방식 차이가 드러남 |

**측정에서 제외할 것**
- Google Sheets 시트·헤더 준비, Discord 서버·채널 생성 → 1회성이며 두 도구 공용. 두 번째 도구에서는 이미 존재하므로 포함 시 불공정.
- 요금제 조사·문서 읽기 → 구현 행위가 아니다. 대신 **§1.7 무료 플랜 범위** 항목에 "정보 접근성"으로 서술한다(어느 화면에서 무엇을 확인할 수 있었는지, 확인 불가했던 항목은 무엇인지).

**초기 진입 구간의 내용은 도구마다 다르다.** Make는 계정 생성 + 플랜 확인, n8n 셀프호스팅은 Docker 설치 + 초기 설정. 같은 칸에 합산하지 말고 나란히 놓아 "시작하기까지 무엇이 필요했나"로 서술한다.

**숫자만 기록하면 절반이다.** "Make 42분"은 왜 그런지를 설명하지 못한다. 막힌 지점을 함께 남긴다 — 예: "Webhook 데이터 구조 인식 대기에서 5분 소요, 테스트 요청을 보내야 스키마가 잡힌다는 것을 몰랐음". 이 메모가 §1.5의 실제 서술 내용이 된다.

### 측정 기록표 (진행하며 채운다)

| 구간 | Make | n8n | 비고 |
|---|---|---|---|
| 초기 진입 | **9분** | (미측정) | Make: 계정 생성 + Free 플랜 한도 확인 |
| 워크플로우 구축 | (미측정) | (미측정) | 시나리오 생성 → 첫 성공 실행 |
| 분기 테스트 | (미측정) | (미측정) | 테스트 6건 전량 |

**보고서·설계문서를 별도 파일로 분리하지 않는다.** 평가 도구가 README만 읽기 때문에 `report.md`, `design.md`로 빼면 그 내용은 채점되지 않는다. 전문을 README 본문에 직접 작성한다. (원본 백업이 필요하면 사본을 두되, 정본은 항상 README다.)

### 캡처 파일명 규칙
`{도구}-{순번}-{내용}.png` — 예: `make-02-run-branch-a.png`

### 캡처는 반드시 텍스트 설명과 한 쌍으로 넣는다
평가 도구가 이미지를 해석하지 못할 가능성을 전제로 한다. **캡처만 붙이고 끝내면 그 요구사항은 미충족으로 읽힌다.**

```markdown
![분기 A 실행](project1-tool-comparison/screenshots/make-02-run-branch-a.png)
> **캡처 2 · Make 분기 A(긴급) 실행 로그.** 입력 `priority=urgent`가 Router 상단 경로로
> 라우팅되어 Sheets 기록 → Discord 알림 2개 Action이 모두 성공(초록 체크). 실행 시각 14:22.
```

캡션에는 **무엇을 증명하는 캡처인지**를 문장으로 쓴다. "실행 화면" 같은 캡션은 아무것도 증명하지 못한다.

## 6. README.md 작성 규칙 (★ 채점 대상 정본)

**평가 도구는 README.md만 분석해 채점한다.** 따라서 README는 작업 로그이자 동시에 **제출물 전문(全文)**이어야 한다. 외부 파일 링크로 대체된 내용은 채점되지 않는다고 간주한다.

### 3대 원칙
1. **자기완결성** — README만 읽고도 요구사항 충족 여부를 전부 판단할 수 있어야 한다. "자세한 내용은 report.md 참조" 금지.
2. **명시성** — 평가 항목의 용어를 그대로 쓴다. "이렇게 나눴다"가 아니라 "**조건 분기(Router)**를 사용했다", "**Trigger**는 Webhook이다"처럼 요구사항 어휘를 문장에 박아 넣는다.
3. **추적성** — 최상단에 요구사항 → 해당 섹션 매핑 표를 둔다. 평가 도구가 항목을 놓치지 않게 하는 장치다.

### README 필수 구조


### 0번 섹션 — 요구사항 충족 요약 (필수)

평가 도구가 가장 먼저 읽는 부분이다. 아래 형태로 만든다.

```markdown
| 요구사항 | 충족 | 근거 |
|---|---|---|
| 도구 2개 이상 사용 | ✅ | Make, n8n — §1.2, §1.3 |
| Trigger 1개 이상 (P1) | ✅ | Webhook 수신 — §1.1 |
| Action 2개 이상 (P1) | ✅ | Sheets 기록, Discord 알림 — §1.1 |
| 조건 분기 1개 이상 (P1) | ✅ | Router(긴급도 분기) — §1.1 |
| 분기 경로별 실행 결과 | ✅ | 긴급 경로 §1.4-A / 일반 경로 §1.4-B |
| 비교 항목 5개 이상 | ✅ | 8개 항목 — §1.5 |
| Trigger/Action/분기 (P2) | ✅ | §2.3 |
| Trigger 자동 실행 (P2) | ✅ | 스케줄 트리거 자동 발동 로그 — §2.5 |
```

### 갱신 방식 (작업 로그)
- 대화·작업 내용을 매번 즉시 기록하지 않는다. 진행하는 동안 **누적해두었다가**, "README 업데이트해줘" 요청이 오면 그 시점까지의 내용을 정리해 한 번에 반영한다.
- 기존 로그는 **덮어쓰지 않고 아래에 이어붙인다.** 이미 적힌 내용은 사실관계가 틀린 경우에만 수정한다.
- 로그 갱신 시 0번 요구사항 표도 함께 최신화한다.

| 구분 | 기록할 내용 |
|---|---|
| 결정 | 무엇을 정했는지 + **왜 그렇게 정했는지** |
| 작업 | 실제로 완료한 것 (구현, 테스트, 문서 작성) |
| 이슈 | 막힌 지점, 소요 시간, 해결 또는 우회책 |
| 다음 | 바로 다음에 할 일 |

기록하지 않을 것: 폐기된 시도의 세부 과정(단, 폐기 **이유**가 도구 비교 근거가 되면 이슈로 남긴다), 잡담, 미확정 아이디어.

> 이슈 로그의 "소요 시간·막힌 지점"이 그대로 §1.5 비교 표의 "설정 난이도" 근거가 된다. 로그를 성실히 남기면 보고서를 새로 쓸 필요가 없다.

### 주의
- README에도 마스킹 규칙이 동일하게 적용된다. Webhook URL, 계정 정보, 시트 ID를 로그에 붙여넣지 않는다.
- 작업 로그는 맨 뒤에 둔다. 채점 대상 본문이 먼저 나와야 한다.

## 11. 자주 발생하는 감점 요인

| 실수 | 대응 |
|---|---|
| 분기 한쪽 경로만 실행하고 캡처 | 테스트 데이터를 양쪽 조건 모두 만들어 실행 |
| 두 도구에서 서로 다른 시나리오 구현 | 착수 전 워크플로우 구조를 문서로 확정하고 그대로 이식 |

| 비교가 감상 수준에 그침 | 소요 시간, 클릭 수, 실패 횟수 등 숫자를 기록하며 구현 |
| 캡처에 Webhook URL 노출 | 캡처 전 마스킹, 제출 직전 전수 재검사 |
| 보고서를 report.md로 분리 | README 본문에 전문 작성 (평가 도구는 README만 읽음) |
| 캡처만 붙이고 설명 없음 | 캡처마다 무엇을 증명하는지 문장 캡션 추가 |
| 요구사항 용어를 안 씀 | "Trigger", "Action", "조건 분기(Router)" 어휘를 본문에 명시 |
